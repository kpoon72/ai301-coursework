# Rubric: is this reproduction package ready to post?

Each check reads the thing itself against the issue, never the write-up's
shape. Headings, length, tables and confident wording never pass or fail a
check on their own. The "Does NOT fail" clauses are part of each pass
condition: apply them before failing anything.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment record (tool version, OS/platform, and any build or install detail), read against the environment the issue reports the bug on (issue body, repo-facts template asks) | Passes when the report names at least the tool's version and the OS/platform it ran on, AND that environment can exhibit the bug as the issue scopes it. Fails if any of: (a) no environment is recorded at all (no version and no OS); (b) the issue scopes the bug to a platform, build type or configuration (title or body says "on Windows", "release builds", "with setting X") and the report neither records that it ran there nor names the difference; (c) the version tested is OLDER than the version the issue reports the bug on (or than "latest"/"main" when the issue says it confirmed there), since an old release cannot show that the reported bug exists today. Does NOT fail: testing a newer version than the issue's; a different OS when the issue does not tie the bug to its OS; any difference from the reporter's environment that the report itself names (the honest cannot-reproduce case). | required |
| Steps re-runnable | The reproduction steps in the repro report (commands, inputs, config), read against the trigger conditions the issue states | Passes when a stranger holding only the posted comments and the issue could re-run the attempt: the commands or actions are given, the inputs are given or pointed at exactly ("the issue's script verbatim", "the exact 12 lines from the issue"), and the issue's trigger conditions (flags, options, driver, input shape) are kept. Fails if any of: (a) there are no steps, only narration ("happens to me all the time"); (b) a step depends on material the reader cannot get (a private repo, an internal config, "our company setup"); (c) the steps silently drop or change a trigger the issue names (a flag, driver, option or input the issue says is needed) without saying so. Does NOT fail: interactive steps described in words ("focus new.txt, press s"); pointing at the issue's own input instead of pasting it; a trimmed output excerpt. | required |
| Behavior matches issue | The observed artifacts in the repro report (pasted output, error text, logs, rendered result), read against the specific failure the issue describes (its error message, symptom, or wrong value) | Passes when the pasted artifact shows the SAME failure the issue describes, triggered by the issue's input: the same error or panic text, the same wrong output, the same missing header/value. Also passes for an honest cannot-reproduce when the artifact shows the observed non-failing output of an attempt that used the issue's trigger. Fails if any of: (a) there is no artifact, only prose describing what happened; (b) the artifact shows a DIFFERENT failure (a different error message, a parse error from a changed input, a validation error instead of a panic, garbled output instead of a crash); (c) the artifact shows only setup or that the program runs (version output, a session list, "tabs are present") and not the failure itself. A report calling its artifact "the same class of failure" does not make it so: compare the text. | required |
| Outcome stated honestly | The repro report's stated conclusion (and the claim comment's statements about the reproduction), read against what the artifacts actually show | Passes when every claim about the outcome is backed by an artifact in the package: "reproduced" is backed by an artifact that passes Behavior matches issue; a cannot-reproduce says so plainly and names what differed. Fails if any of: (a) the report or claim asserts a reproduction, confirmation, or "root cause" that no artifact in the package shows; (b) a causal diagnosis is stated as verified with no code, log, or experiment shown for it; (c) the conclusion calls a different failure the issue's bug. Does NOT fail: a clearly labelled hypothesis ("suggests", "looks like", "I think"); an honest cannot-reproduce. | required |
| Claim comment specific and scoped | The candidate claim comment, read against the issue | Passes when the claim names something specific to this issue (its component, behavior, command, or a pointer from the thread) and states a concrete next step that is investigation or verification. Fails if any of: (a) it is a +1, "any updates?", or complaint with no next step; (b) it asks a maintainer to assign the issue or reserve it, or says "assigning myself"; (c) it promises a fix by a date or "guaranteed"; (d) it is generic boilerplate that would read the same on any issue. Does NOT fail: stating the intent to work on it ("I'd like to take this", "I'd like to pick this up", "I'm working through this"), which is what a claim is; mentioning a planned fix direction as a plan ("make it warn or stash with --include-untracked"); saying "report back"; being short. | required |
| Repo AI policy honored | The repo-facts block's contribution policy (AI-use and disclosure rules), read against the claim comment and repro report | Passes when the package meets every AI-related rule the policy states for comments or issues. If the policy requires disclosure of AI assistance in comments/issues or "all AI usage in any form", the package must contain a disclosure statement (tool used and extent), and fails without one: these comments are drafted with AI assistance in this course, so silence is non-disclosure. Does NOT fail: no stated AI policy; a policy whose disclosure ask covers only pull requests or code (not comments); a policy asking only that humans understand the work or write in their own words, when the comments read as specific first-person writing. | required |
| Template asks covered | The repo-facts block's bug-report template asks, read against the repro report | Passes when the report supplies the template's environment and reproduction asks (version, OS, steps, actual, expected) or explains a gap. | preferred |

## Verdict rule

accept if every required check passes; preferred checks never change the
verdict. unclear counts as fail for required checks. In live mode on a
claim-only draft, only "Claim comment specific and scoped" and "Repo AI
policy honored" are graded (the other required checks report unclear with
"not yet applicable: claim-only draft" and are left out), and the verdict
is accept when both pass.
