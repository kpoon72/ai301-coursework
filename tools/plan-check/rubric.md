# Rubric: is this plan ready to post and build from?

Each check reads the plan itself against the issue and its repro evidence,
never the write-up's shape. Headings, length, and confident wording never
pass or fail a check on their own. The "Does NOT fail" clauses are part of
each pass condition: apply them before failing anything.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis fits the repro | The plan's stated cause (its diagnosis) and the plan comment's cause claim, read against every step AND every control run in the repro-evidence block, and against any cause a maintainer (OWNER/MEMBER/COLLABORATOR/CONTRIBUTOR) states in the thread | Passes when the stated cause explains the repro's failing steps AND is consistent with its control runs. Fails if any of: (a) a control run shows the part the plan blames working correctly (e.g. the plan blames the collect operator but the control shows top-level collect returns `[null]`; blames a missing module but the control shows that module firing on another path; blames a tokenizer but the control shows the same items parsing without the flag); (b) a repro step pins where the failure happens and the plan puts it somewhere else (e.g. the step shows the value is already wrong before the stage the plan blames); (c) the plan dismisses part of the evidence as a "red herring" or "side effect" without explaining it; (d) the plan contradicts a maintainer's stated cause in the thread without addressing it. Does NOT fail: a diagnosis taken from the issue or thread that the repro is consistent with; naming an unconfirmed detail (the exact line, the exact layer) as an unknown; the plan's own account of WHY a control behaves as it does (e.g. why a cache clear gives one clean run) — that is the plan explaining the control, not contradicting it, and the check only asks whether some control shows the blamed part working correctly. | required |
| Change targets the cause | The plan's change/approach section read against its own diagnosis and the repro evidence | Passes when the change acts on the code the diagnosis and evidence locate. Fails if any of: (a) the change works around the symptom instead of fixing the located cause, e.g. documentation-only when the evidence and thread locate a code defect, or a catch-all (`recover()`, blanket try/except around a runner) that hides the failure; (b) the change repairs output after the damage when the evidence shows the damage happens earlier (e.g. re-padding values that were already lost). Does NOT fail: a small guard at the exact failing site (clamping a subtraction, catching the specific exception the function should handle); deferring a larger rework the thread discussed. | required |
| One bounded change | The plan's scope statement, list of proposed changes, and files/areas, read against what the issue asks for | Passes when the plan makes one change that fixes this issue, plus regression tests. Fails if the plan includes ANY of: rewriting or restructuring a subsystem or module; a dependency upgrade or library migration; a new user-facing option, setting, or prop; a unifying abstraction across components the issue does not involve; a CI matrix or pipeline rework; "while I'm in there" fixes to other issues or behaviors; a PR series that starts with anything other than the fix. Does NOT fail: auditing or fixing sibling sites of the SAME defect pattern in the same function; touching two or three files for the fix plus tests; stated deferrals ("not in scope: X"); noting a related bug to file separately. | required |
| A stranger could start | The plan's files, approach steps, and scope read as instructions to someone who has never seen the issue | Passes when the plan names the file(s) and the function or specific code area it will change, and the concrete edit, so a stranger could begin without asking the author anything. Fails if any of: (a) the steps are investigations with no stated change ("look into", "dig into", "profile to find the slow parts", "figure out what happened", "fix it once the cause is clear"); (b) the plan does not know which component or layer it will change ("gocui? tcell? not sure"); (c) the location is vague ("somewhere around linter execution"); (d) the plan lists optional add-ons ("maybe also check other linters"). Does NOT fail: the file and component are named and the exact function will be pinned during the build by a stated method (debug logs, tracing a named call) — that is a named unknown, not vagueness. | required |
| Test plan is observable | The plan's test plan read against the repro evidence's steps and artifacts | Passes when the test plan re-runs the repro (or names a specific test) and states the concrete result that proves the fix: an exact output, value, return, exit code, count, or the absence of a named artifact. Fails if the expected result is an impression ("should feel fast", "look much better", "work correctly", "nothing else should feel broken") or names no observable outcome. Does NOT fail: expected results given as "matches the python engine's output" or "the control stays unchanged" when those outputs are in the repro evidence. | required |
| Unknowns stated honestly | The plan's risks/unknowns and the certainty of its diagnosis and comment | Passes when the plan claims no more certainty than its evidence supports: anything unverified is labelled as an unknown or risk. Fails if the plan or comment asserts as settled its central cause, or a fact the change depends on, when no evidence in the package shows it ("the root cause is X, not Y" with nothing shown for X; "I dug into this and the root cause is..." with no artifact). Does NOT fail: "Risk: none identified" with a reason; a short plan with no risks section when its diagnosis is taken directly from the evidence; a supporting explanatory detail inside a diagnosis that already fits every repro step and control (e.g. how a fresh path differs from the failing one), since "Diagnosis fits the repro" has judged that grounding. | required |
| Comment respects thread and repo | The candidate plan comment read against the thread highlights (who said what, their role) and the repo-facts block's contribution policy | Passes when the comment is consistent with what the thread and repo already say. Fails if any of: (a) a maintainer (OWNER/MEMBER/COLLABORATOR) in the thread has stated the cause, the direction, or posted a patch, and the comment neither follows it nor says why it departs; (b) the repo's policy requires AI disclosure in comments/issues or for "all AI usage in any form", and the comment has no disclosure line naming the tool and extent (these comments are drafted with AI assistance in this course, so silence is non-disclosure); (c) the comment promises a PR or fix by a calendar deadline ("this week", "by Friday"); (d) it piggybacks ("same approach as above") instead of stating its own plan. Does NOT fail: no stated AI policy; a policy whose disclosure ask covers only pull requests; "I'll report back / open the PR once tests pass" (a condition, not a date); a thread with only non-maintainer comments that the comment does not mention. | required |

## Verdict rule

accept if every required check passes. There are no preferred checks. A
check graded unclear (the evidence it needs is genuinely absent from the
package) counts as fail. One failing required check is enough to reject.
