# Rubric: is this pull request ready to submit?

Each check reads the PR itself against the plan, the issue, and the repo's
stated asks, never the write-up's shape. Length, headings, commit count, and
confident wording never pass or fail a check on their own. The "Does NOT
fail" clauses are part of each pass condition: apply them before failing
anything. Checks 1-3 cover silent drift, 4-5 not tested, 6 unreviewable,
and 7-8 the standards wall.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff stays inside the plan | Every changed file and hunk in the diff, and every commit in the commit list, read against the plan's scope, its approach steps, its "not in scope" lines, and its deviation notes | Passes when every hunk is the planned fix, a test for it, or a change a deviation note (in the plan or restated in the description) names. Fails if the diff adds anything the plan neither names nor scopes in: a new config option, setting, CLI flag, or public API; a refactor, rename, or rewrite of code the fix does not need; rewording or behavior changes in unrelated features; a dependency bump; a change to a file the plan never touches. Fails harder when the plan explicitly scopes that thing out. Does NOT fail: the tests the plan asks for; a CHANGELOG/whatsnew/i18n/docs entry the repo's template asks for; a small helper or one-line edit inside the planned function that the fix needs; tests inside the same source file in languages with inline tests. | required |
| Plan delivered or shortfall disclosed | Each change and each file the plan promises, read against the diff; then the plan's deviation notes and the description for any stated deferral | Passes when every change the plan promises appears in the diff, OR each missing one is named as deferred or dropped in the plan's deviation notes or the description, with a reason. Fails if a planned change (a code change, a doc update, a test the plan names) is absent from the diff and nothing says so. Does NOT fail: a deferral recorded in the plan and restated in the description, even if it leaves a known limit in place; the plan's own optional or "not in scope" items. | required |
| Description matches the diff | Every factual claim in the PR title and description (what changed, "exactly as planned", "no other changes", "docs now document", "CHANGELOG entry added", "tests added"), read against the diff and commit list | Passes when every claim about the change is visible in the diff and nothing the diff does is denied by the description. Fails if the description claims fidelity the diff contradicts ("implements the plan exactly", "no functional changes outside X", "exactly as planned" over a diff with unplanned work), or claims a change (docs, changelog, test, file) the diff does not contain. Does NOT fail: a terse description that claims little; describing the fix at a higher level than the code, as long as nothing stated is false. | required |
| Plan's repro re-run before and after | The test-evidence section (and any before/after in the description), read against the plan's test plan and the repro evidence it built on | Passes when the evidence re-runs the plan's repro on the failing path (the exact input, command, or scenario that broke) on the branch and shows the observable after-result the test plan expects (an output, value, exit code, count, or diff), with the before shown or stated from the repro. If the plan's test plan names more than one failure mode or repro, each one is re-run. Fails if any of: (a) the evidence is a statement instead of an observation ("tested locally, works now", "verified working on my machine for a day", "all tests pass" alone); (b) it exercises a different or unchanged path than the one the plan's repro breaks (a control case only, a single-file case when the bug is multi-file, a GET when the bug is a POST); (c) a failure mode or repro the plan's test plan names is never re-run. Does NOT fail: before-output taken from the plan's repro evidence instead of re-run; controls shown in addition to the repro; a terse transcript that shows the after-result. | required |
| Repo's own checks run with results | The test-evidence section and description, read against the test commands the repo's template or contributing guide names (or, live mode, the four checks Path Review's PR template lists: make test-unit, make test-integration, make lint, make typecheck) | Passes when the evidence names the repo's suite or check command(s) actually run and states each one's result (passed with a count or clean, or a failure disclosed with its reason). Fails if no suite or check command is named at all ("all tests pass", "tests added; all tests pass" with no command), or, where the repo names specific checks, one of them is missing with no reason given. Does NOT fail: a named suite subset scoped to the changed area (e.g. `cargo test -p ignore`, `pytest tests/io/parser`); a check that fails or runs no tests, reported as-is with its reason. | required |
| Diff carries no debris | Every hunk in the diff, plus the commit messages, read for content that is not part of the fix or its tests | Passes when every added or changed line serves the fix, its tests, or a repo-required entry. Fails if the diff contains any of: a debug print or log left in (`eprintln!("DEBUG`, `print(`, `console.log`); commented-out code (an old attempt, a disabled debug line); a dead function or variable added but never used, or kept alive with an allow/ignore attribute; a TODO/FIXME added; whitespace, re-indent, import-reorder, or re-printed-identical-line churn in code the fix does not change. Commits named "wip", "fix", "misc cleanups while debugging", or "fmt pass" support a fail but never fail the check alone. Does NOT fail: formatting the lines the fix itself changes; a comment explaining the fix. | required |
| Repo's PR asks honored | The repo-facts PR-template and contributing asks (live mode: `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`), read against the title, description, and diff | Passes when every ask that a PR can visibly satisfy is met: each required template section has real content (not left as the placeholder), a required issue-link line ("closes #N", "fixes #N") names the issue, a required checklist is filled in honestly, and a required artifact (CHANGELOG/whatsnew entry, i18n text, conventional-commit title) is in the diff or title. Fails if a required section, issue-link line, checklist, or artifact is missing or left as the placeholder. Does NOT fail: a repo with no template and no stated PR asks; an ask the PR says does not apply, with a reason; process steps outside the PR text (CLA, vouch flow, sign-off) that the package cannot show; a checklist box left unticked because it is honestly not yet true (e.g. CI before the PR is opened). | required |
| AI use disclosed where required | The repo's stated AI policy (repo-facts contribution policy; live mode: CONTRIBUTING/AI policy plus the course's always-on disclosure ask), read against the description | Treat every PR as AI-assisted work. Passes when the repo has no stated AI policy and (live mode excepted) no disclosure is asked, OR the policy asks for disclosure and the description has a disclosure in the author's own words naming the tool and how it was used. Fails if the policy requires disclosure of AI use in PRs or "all AI usage in any form" and the description has no disclosure line, or the disclosure names neither the tool nor the extent. In live mode the course always asks for this disclosure in Notes for Reviewers, so it is always required there. Does NOT fail: a policy whose ask covers only issues or comments, when the PR text is in the author's own words. | required |
| Title says what changes | The PR title, read against the diff | Passes when the title names the behavior the fix changes, specific to this issue. Fails if the title is generic ("Fix bug", "Update file", "fixes #12"). | preferred |

## Verdict rule

accept if every required check passes; reject if any required check is fail
or unclear. Unclear (the evidence the check needs is genuinely absent from
the package) counts as fail. The preferred check ("Title says what changes")
is reported but never changes the verdict. One failing required check is
enough to reject. A shortfall the plan's deviation notes or the description
discloses is graded by "Plan delivered or shortfall disclosed" and does not
by itself fail any other check.
